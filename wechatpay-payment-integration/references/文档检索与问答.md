# 文档检索与问答

在 `<SKILL目录>/assets/微信支付官网文档/` 知识库内，先用关键词 **全局** `Grep` **探路**，再根据命中路径与用户语义 **缩小范围** 并 `Read` 精读。

回答所依据的正文须来自 `<SKILL目录>/assets/微信支付官网文档/` 内经 `Read` 读取的 Markdown；仅当知识库未收录时，才按[链接与联网](#链接与联网)取官方页补充。

## 规则

### 硬性约束

1. **先探路再锁定**：可依据已有线索（前置检索给出的定位信息、用户给出的 URL/路径）做定向 `Grep`；**没有这类依据时**须在 `<SKILL目录>/assets/微信支付官网文档/` **全树**上 `Grep`，不得在未看命中分布的情况下仅凭知识库索引猜测并锁定单一前缀。定向 `Grep` 零命中或不贴题时回退全树。
2. **路径即判据**：文件名和目录已包含中文标题，路径明显相关时直接精读，**不要**批量读 `front matter` 做筛选。
3. **检索词忠实**：`Grep` 的 `pattern` 须保留用户原文中的 URL、接口路径、错误码、字段名等。
4. **精读节制**：只读最相关的 **1～3 篇**正文，不要大面积扫描；缩小范围后的 `Grep`/`Read` 应落在第三步确定的前缀或少数候选前缀内。
5. **引用前取** `url`：最终引用的文档须读 `front matter` 取 `url`，禁止自行拼接链接。
6. **禁止编造**：接口、字段、错误码须来自知识库 `Read` 结果，不凭模型记忆编造。
7. **知识库未覆盖时如实告知**：若经充分检索仍未找到相关文档，应明确告知用户该问题超出当前知识库覆盖范围，不要硬凑答案。
8. **简洁作答**：答案只含直接回答用户问题所需的信息；用户未问的不展开，不堆砌无关内容。

### 澄清话术

对照 `<SKILL目录>/assets/wechatpay-docs-guide.md` 第五节「用户描述模糊时的澄清话术」判断是否需要澄清：用户原文命中触发词（如「证书」「API证书」「券」「密钥」等），但没有说出该类别下某个具体产品名称 → **只输出对应澄清话术并停止**，不得先行检索或作答。

### 角色与 API 版本判定

本节结论只有两处用途：**第三步收敛检索范围**，以及跨多角色时停下来询问用户。

判定顺序：**`AGENTS.md` 已记录 → 用户原文可识别 → 看第二步命中分布**。前者命中即可停止判定。

> **对比类问题例外**：用户显式要求对比多个角色或版本（如「V2 和 V3 的分账有什么区别」）时，本节整节不适用，用户要对比的各侧分支全部保留。

- **商户身份**（无默认值，歧义时必须停下来问）：

  1. 读项目根目录 `AGENTS.md`，已记录角色则直接采用。
  2. 否则按 `<SKILL目录>/assets/wechatpay-docs-guide.md` 第三节「角色与文档路径对照」的角色特征（`mchid`→普通商户、`sp_mchid`→服务商、`brand_id`→品牌商户等）从用户原文识别。
  3. 仍无法确定的，看第二步命中路径分布：集中于单一角色则按该角色收敛；**跨多角色则立即停止**——本轮不得 `Read`、检索或作答，只输出：

     > 找到了以下角色下的相关文档：[列出命中的角色]。请问您需要全部查看，还是只看某个角色的文档？

     用户回复后，**先**询问是否将该角色写入 `AGENTS.md`（同意则写入，后续会话自动采用，用户可随时自行修改）；无论同意与否，确认完毕才可继续检索。

- **API 版本**（有默认值，不停下来问）：同样先查 `AGENTS.md`。未记录时，用户已明确指定的以用户为准；无从判断且 `APIv2`/`APIv3` 两侧均有文档时，默认优先 **APIv3**（`APIv2` 仅当 V3 侧无对应文档时再查）。用户明确指定版本的，可在**本轮作答之后**询问是否写入 `AGENTS.md`，该询问不阻塞本轮检索与作答。

### 链接与联网

正文中遇到的链接按以下方式处理：

| 域名 | 处理 |
|---|---|
| `pay.weixin.qq.com` | **优先**在 `<SKILL目录>/assets/微信支付官网文档/` 内用 `Grep`（URL 路径片段、文档标题、`doc` 路径、文档 ID 等）定位对应 `.md` 再 `Read`；知识库内**未找到**对应或等价文档时，可对该 URL 使用 `WebFetch` |

其他外链先询问用户是否联网。

## 核心工作流（必须按顺序）

> 建议顺序：**读索引、理解问题、拟检索词** → `Grep` **探路（定向或全树）** → **结合命中与语义缩小范围** → **聚焦** `Grep` **/** `Read` → **作答**。

### 第一步：读索引、理解问题、拟定检索词

1. `Read` **`<SKILL目录>/assets/wechatpay-docs-guide.md`**（每题一次），弄清知识库结构和检索路径。该文件含三级目录树、业务目录结构、角色与文档路径对照、单篇文档结构（文件名与 front matter）、澄清话术。
2. 按 `<SKILL目录>/references/如何理解用户问题.md` 润色、纠错、指代消解。
3. 按[澄清话术](#澄清话术)规则检查是否需要澄清——命中触发词且用户未指明具体产品时，只输出澄清话术并停止，不进入后续步骤。
4. 按[角色与 API 版本判定](#角色与-api-版本判定)查 `AGENTS.md` 并从用户原文识别角色与 API 版本，记录下来供第三步收敛使用；此处识别不出的留到第三步按命中分布判定。
5. **拟定检索词**：抽出 **1～3 个**用于首轮 `Grep` 的 `pattern`，优先用户原文中的 URL、接口路径、错误码、字段名、产品官方名等；`pattern` 须具体、可命中，避免过宽（如单独搜「支付」）或过窄导致零命中。用户给出官网链接或文档 ID 时，从中提取纯数字 `doc_id` 作为 `pattern`。已有线索给出的产品名、接口名可一并纳入。

### 第二步：`Grep` 探路

已有线索足以定位产品或接口时，先在对应前缀下定向 `Grep`，零命中或不贴题即回退全树；否则在 `<SKILL目录>/assets/微信支付官网文档/` **全树**下用第一步的 `pattern` 做 `Grep`（可换 `pattern` 各搜一轮）。

无论走哪条分支，都关注：

- **命中文件的路径和文件名**：路径自带中文目录名和文档标题（如 `支付产品/JSAPI支付/开发指引-4012791870.md`），直接判断是否与问题相关
- **命中片段语义**：是否与用户要问的内容一致
- **命中数量**：过多则换更具体的 `pattern`；为零则放宽或换同义官方用词再搜一轮
- **路径分布**：是否集中在某一 `APIv2`/`APIv3`、`普通商户`/`合作伙伴` 分支，或 `brand/品牌商户/`（品牌经营平台，独立体系），还是跨多个分支

本步目的是用**真实命中**校准检索方向，而不是先猜目录。

### 第三步：结合命中与用户语义缩小范围

综合第二步结果与用户问题含义：

1. **以命中路径为主**：路径明显相关时直接进入第四步精读，**不需要**额外读 `front matter` 确认。命中含明显无关分支时，结合用户表述与 **`<SKILL目录>/references/基础概念及业务介绍.md`** 筛掉，勿凭猜测丢弃仍有相关命中的分支。
2. **收敛角色与版本**：按[角色与 API 版本判定](#角色与-api-版本判定)锁定——跨版本按默认值取舍，**跨多角色则必须停止并询问用户**（不得自行筛选分支或继续检索）。**对比类问题不适用本条**，各侧分支均保留。
3. **索引作辅助**：当命中分散或难以取舍时，再 `Read` `<SKILL目录>/assets/wechatpay-docs-guide.md` 目录树，对照叶节点标注判断哪条路径更贴题；若索引判断与 `Grep` 命中冲突，**以与问题更相关的命中文件为准**。

**筛选目标：锁定最相关的 1～3 篇文档。**

若缩小后仍无足够相关正文：回到第一步调整 `pattern`，或回到第二步改走全树探路、对候选分支**分前缀再各做一轮** `Grep`。**累计约 3 轮仍无相关命中即停止重试**，按硬性约束「知识库未覆盖时如实告知」处理，不要降格用弱相关文档硬凑答案。

### 第四步：聚焦 `Grep` / `Read`

1. 在第三步确定的前缀下，用更精确的 `pattern` 做聚焦 `Grep`。
2. `Read` 最相关的 **1～3 篇** `.md`：**先从文件头读起**（行 1 起）以取得 `front matter` 的 `url` 并了解文档结构；正文较长时，再用 `offset`/`limit` 定位到与问题直接相关的段落，不要整篇通读，也不要只读开头就作答。
3. 同一文档 ID 可能存在请求示例副本，接口说明以**主文件**为准；示例代码文件仅在需要代码示例时 `Read`。

> **对比类问题**：每个分支各取 1 篇，总数仍控制在 1～3 篇内。

### 第五步：作答

- **极简**：只答用户所问，先给结论或做法，再补必要细节；不扩背景、不复述检索、不贴文档原文。
- **可溯源**：每条结论都对应到已 `Read` 的知识库文件，或知识库未收录时经 `WebFetch` 取得的 `pay.weixin.qq.com` 正文（须在答案中注明来源 URL）。
- **「⚠️ 注意事项」**：仅直接踩坑风险时输出，无则省略整个段落。
- **「📋 相关文档」**（必须）：仅列出答案中**实际引用**过的知识库 `.md`，**最多 3 条**，按相关度从高到低排列。本地路径从 `APIv2/`、`APIv3/` 或 `brand/品牌商户/` 起算；官网链接取 `front matter` 的 `url` 去掉末尾 `.md`，尚未取到 `url` 的补读 `front matter`（`offset` 1、`limit` 5），无 `url` 则写 `（本文件 front matter 无 url，勿编造）`。

#### 作答格式

```markdown
## [简短答案，直接回答用户问题]

### 📋 相关文档
- **`{本地文件路径}`**：`{front matter url 去掉 .md}`
- ...（最多 3 条）

### ⚠️ 注意事项
- [注意点]
```

## 示例

**用户**：「合作伙伴 `APIv3` 合单 JSAPI 下单里 `sub_mchid` 怎么传？」

1. 第一步：读索引；润色、消解问题；从原文确认角色「合作伙伴」、版本 `APIv3`；拟定 `pattern`：`sub_mchid`、`合单`、`JSAPI`。
2. 第二步：线索已指向产品「合单支付」、商户类型「服务商」、版本 `v3`，足以定位，先在 `APIv3/合作伙伴/` 下定向 `Grep`，观察命中路径（如 `APIv3/合作伙伴/支付产品/JSAPI合单支付/...`），从文件名和目录直接判断相关性；若零命中或不贴题，回退全树 `Grep`。
3. 第三步：结合「合作伙伴」「`APIv3`」与命中分布，将精读范围收敛到 `APIv3/合作伙伴/支付产品`。
4. 第四步：在该前缀下聚焦 `Grep`，`Read` 最相关的 1～2 篇 `.md`。
5. 第五步：从已读文档的 `front matter` 取 `url` 作答。
