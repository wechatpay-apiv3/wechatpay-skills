# 产品、角色、API 版本与验签方式的确认

> 用于编码意图：开始编写支付相关代码前，确定本次接入的**微信支付产品、商户角色、API 版本、验签方式**。
>
> 本文只讲**怎么判断、怎么与用户确认**。各要素的定义、取值范围与官方默认规则见 [基础概念及业务介绍](./基础概念及业务介绍.md)，不在此重复。

## 一、总原则

**可以推测，但不得静默使用。** 必须把推荐结论、依据和不确定点一并展示，经用户确认后才能用于编码。

推荐结论按以下依据形成：排在前面的依据决定推荐值；**排在后面的依据不被丢弃**，转为向用户补充说明的内容。

| 依据来源 | 怎么形成推荐 | 怎么向用户表述 |
| --- | --- | --- |
| **用户在本次对话中明确说明** | 无需另作推荐 | 复述其说明并请其确认 |
| **存量工程中可验证的既有实现** | 以存量实现作为推荐值，**不主动推动改造**；三种情况见 2.2 | 说明这是工程现状并给出证据位置；与官方推荐不同时，说明两者差异，并注明本次不作改动 |
| **官方默认与推荐**（见基础概念文档） | 前两者都没有时，以官方默认作为推荐值 | 明确说明这是官方默认值，不是依据本工程得出的结论 |

无论推荐值来自哪一层依据，都必须展示并经用户确认后才能用于编码。

## 二、怎么从工程判断

### 2.1 从工程证据能推出什么

查看用户项目的配置文件、支付相关代码与依赖声明，按下表对照。**推荐结论必须附上证据位置**（文件路径与配置项/代码位置），便于用户核对。

| 要素 | 可查的证据 | 可信度 |
| --- | --- | --- |
| **API 版本** | XML 报文、MD5 / HMAC-SHA256 签名、32 位 API 密钥 → APIv2<br>JSON 报文、`Authorization: WECHATPAY2-SHA256-RSA2048` → APIv3<br>`WECHATPAY-BRAND-SHA256-RSA2048` → brand（品牌经营） | 高 |
| **验签方式** | 配置或代码中有 `wechatpay_*.pem`、平台证书下载或自动更新逻辑 → 平台证书<br>有微信支付公钥文件、公钥 ID 配置 → 微信支付公钥 | 高 |
| **签名凭据** | `apiclient_cert.pem` / `apiclient_key.pem` / `.p12` + 商户证书序列号 → 商户 API 证书<br>独立的品牌证书序列号与私钥 → 品牌 API 证书 | 高 |
| **商户角色** | 配置中出现 `sp_mchid` + `sub_mchid` → 服务商 / 特约商户体系<br>出现 `brand_id` → 品牌经营体系<br>**仅出现 `mchid`** → 信息不足，见 2.3 | 前两项高，第三项低 |
| **支付产品** | **不从工程推断。** 工程证据只能说明存量已接入哪些产品；本次要接的产品由需求决定，须按业务场景在 [产品总览](../assets/wechatpay-product-overview.md) 中匹配候选，由用户明确选定 | 不适用（不作为判据） |

工程中没有任何支付代码时，上述证据基本不存在，应如实说明「无法从现有工程判断」，不要以推测代替确认。

### 2.2 依据存量工程时的三种情况

**① 常规：沿用存量实现**

工程已用平台证书验签，就继续用平台证书，不要因为官方推荐微信支付公钥而改推公钥；可以告知公钥无有效期、维护成本更低，由用户另行决定是否切换。

**② 存量方案与本次需求不兼容**

要说明：存量配置为什么不适用于本次需求、需要新增哪一套配置、两者是并存还是替换关系。

例如工程已有商户 API 证书与 `mchid`，本次要接品牌经营——品牌 API 证书与商户 API 证书是两套独立证书，**不能混用**，且品牌接口走 `brand_id` 而非 `mchid`，需要另行申请和配置。

**③ 存量为 APIv2**

- 在原有 V2 链路上做改动：确认时说明本次沿用 APIv2，不必展开迁移讨论；
- 新增接口或新功能：说明 V3 是主力版本、V2 仅存量维护，并给出两种选择各自的影响，**由用户决定**走哪一套。

沿用存量 V2 不等于推荐 V2；在用户未使用 V2 的场景下，不得主动引导其新接 V2。

### 2.3 商户角色不可凭空推测

商户角色是商户的商业关系，不是能从代码完全读出的技术事实。

- 配置中出现 `sp_mchid` / `sub_mchid` / `brand_id` 等线索时，可据此提出候选并请用户核对；
- **仅有 `mchid` 不足以判定为普通商户**——服务商用自己的商户号调接口同样常见；
- 没有线索时，必须由用户直接告知，不得猜测。

提问时给出可选项与各自影响，让用户正面选择，**不要用「我看你是直连商户，对吧」这类引导式问法**。角色不同会导致接口、报文结构与商户号参数整体不同，选错的返工成本在四项中最高。

### 2.4 验签方式的适用范围

验签方式指 **APIv3 / brand 体系下平台证书与微信支付公钥二选一**。

- 本次接入为 **APIv2** 时，该项**不适用**（V2 用对称密钥 MD5 / HMAC-SHA256 签名验签）。在确认清单中标注为「不适用（APIv2 使用对称密钥签名验签）」，不要向用户提问，也不要省略不提；
- 新接入且无存量约束时，按官方推荐优先微信支付公钥，并说明这是默认选择。

## 三、确认时要展示什么

每一项都要给出：

| 项目 | 要求 |
| --- | --- |
| **结论** | 本次按什么执行 |
| **依据来源** | 标明是「用户已说明」「存量工程」「官方默认」还是「模型推断」——四者可信度不同 |
| **证据位置** | 来自存量工程时，给出文件路径与配置项/代码位置 |
| **不确定点** | 哪些信息不足、还需用户提供什么 |
| **选错的影响** | 至少对商户角色与 API 版本说明影响范围 |

多轮对话中要区分「用户明确说过」与「我从上下文推断」，不得把用户早前的随口提及当作已确认。

用户确认前，不得基于这些结论编写支付相关代码。
