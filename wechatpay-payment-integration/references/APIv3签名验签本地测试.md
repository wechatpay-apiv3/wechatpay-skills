# APIv3 签名验签本地测试

本指引用于 APIv3 接入后的安全自测：由**独立于业务工程源码和生产部署产物的临时测试程序**，调用项目实际使用的签名、应答验签、加解密及回调处理能力，请求微信支付 `POST /v3/security/echo` 并记录逐项实测结果，供 `SKILL.md` 编码意图的统一检测报告汇总。echo 不是支付交易，不验证订单、退款等业务状态。不能用另写的签名实现、独立 demo 或仅凭 `curl` 成功，代替项目代码通过。

## 测试边界与前置条件

1. 确认项目的商户角色、APIv3 配置以及使用微信支付公钥还是平台证书；选用对应角色的官方文档。`Wechatpay-Serial` 按实际加密模式填微信支付公钥 ID **或**平台证书序列号，同一次调用不混用；不要将其与 `Authorization` 中的商户 API 证书序列号混淆。
2. 从业务工程之外的独立测试程序引用/加载项目已有实现及配置，列出实际复用的请求签名、应答验签、敏感字段加解密、通知验签与应答的类/方法或入口。测试程序不得加入业务接口、生产路由或部署包；若现有代码无法从外部调用，先报告阻塞并提出最小接入方案，**不得为跑测试擅改业务代码或另写一套实现冒充复用**。
3. 真正请求微信支付和开放回调地址前，按 `SKILL.md` 的前置确认取得用户同意，说明使用的环境与潜在影响。商户私钥、APIv3 密钥、证书及公钥从现有安全配置读取；不要求用户在对话中粘贴凭据，不写入测试文件、仓库或日志。
4. 若测试回调，准备可由微信支付访问的公网 HTTPS `notify_url`，指向隔离的临时测试接收端，而不是文档示例地址、本机 `localhost` 或业务支付成功路由。该接收端须将原始报文和签名头交给项目已有的通知验签/解密与应答能力；不能接入订单状态更新。没有满足条件的地址则不传 `notify_url`，将真实回调标记为未测。

## 执行与判定

1. 独立测试程序使用项目实际请求签名能力、实际加密模式和一段非敏感的已知明文构造 echo 请求；将加密后的值填入 `encrypted_echo_message`，并记录原始明文作为比对基准。`echo_message` 也使用可识别的非敏感测试值。不使用官方示例中的 `notify_url`；仅在前置条件满足时传入真实测试地址。
2. **请求签名**：项目代码发送真实请求，记录微信支付 HTTP 状态与错误码。返回 `200` 且回显值与请求一致，才认为这次请求签名链路通过；失败需区分签名错误、配置/参数错误与网络错误。成功应答本身不代表项目已完成应答验签。
3. **应答验签**：将收到的原始应答及签名相关响应头交给项目实际验签逻辑，验证原始报文通过；在独立测试程序内复制并篡改应答体后，验证同一逻辑拒绝。负向测试不修改真实应答，不向微信支付回传篡改内容。
4. **敏感字段加解密**：确认上送密文来自项目实际加密方法，使用项目实际解密方法解密微信支付返回的 `encrypted_echo_message`，与加密前的测试明文比对；只核对 HTTP `200` 或返回非空密文均不能判为通过。
5. **真实回调及应答**：传入 `notify_url` 时，确认独立接收端实际收到 `SECURITY_ECHO.SUCCESS`。把原始请求体与签名头交给项目已有回调安全处理能力；验签成功后用 APIv3 密钥解密 `resource`，核对其中 `echo_message` 与请求一致；如有加密回显字段，按官方回调文档及项目解密能力核对。记录验签通过后在 5 秒内返回 `200` 或 `204` 的实际结果，错误签名不得返回成功，也不得将该事件作为支付成功更新订单。若仅复用了项目的验签/解密方法而未经过原业务回调入口，明确报告覆盖范围，不能宣称业务路由已通过。
6. **受控负向回调验证**：只在独立测试程序内用已收到的通知副本篡改报文或签名，交给同一项目验签能力，核对其拒绝并产生失败应答；不得把伪造通知当真实微信回调，也不期待微信支付在本次 echo 中主动发送错误签名。无法复用项目实际应答能力时，将应答项记为未测或受阻。

各项独立判定；前置步骤失败导致后续无法执行时，不得将后续项写为通过或直接归咎于代码。任何修复业务工程或公共方法的动作，其整改范围仍须按 `SKILL.md` 的要求另行取得用户确认，记录问题后再决定是否修改和重测。

## 安全实测结果（统一检测报告的第一块）

出具书面报告时，将结果写入 `wxpay-docs/代码质量检测报告.md` 的 APIv3 安全实测部分，不另行生成同内容的完整报告；用户不需要报告时，在对话中给出同样的逐项实测结论。逐项写「通过 / 未通过 / 未测 / 受阻」和依据：通过须有实际运行证据，未通过指已执行且结果不符，未测指本次未执行，受阻指缺少前置条件或无法调用项目真实方法。附所用项目类/方法或入口、测试程序所在的隔离环境、商户角色与加密模式、请求 HTTP 状态和可安全记录的错误码；不能记录私钥、APIv3 密钥、敏感明文或完整认证信息。每次重测记录新结果及变化，不覆盖未解决项。

| 检查项 | 需记录的观察结果 |
| --- | --- |
| 请求签名与 echo 调用 | 实际调用的项目签名入口、HTTP 状态与错误码、回显是否一致 |
| 应答验签（正向 / 篡改） | 项目验签入口；原报文是否通过，篡改副本是否被拒绝 |
| 上送加密与应答解密 | 项目加解密入口；解密结果是否与原始测试明文一致 |
| 真实回调接收 / 验签 / 解密 | 是否收到通知、项目方法是否验签通过、解密后回显是否匹配；无公网地址时分别注明未测原因 |
| 回调应答（正常 / 篡改） | 实际 HTTP 状态与耗时；项目应答能力是否在错误签名时拒绝；仅测隔离适配器时说明未覆盖业务路由 |

总结已通过、未通过、未测和受阻的项目，给出针对性排查方向与重测条件。独立测试程序及临时回调接收端不得进入业务工程的源码与生产部署产物；结束后关闭临时监听并停止对外暴露的测试地址。若项目代码无法在不修改业务工程的条件下复用，不得用自制实现填补并宣布通过；先报告受阻，修改方案另行征得用户同意。
