# 用流程规则和测试用例检查项目


## 流程
1. 本文件同级的 [流程规则与测试用例](./流程规则与测试用例) 目录下，每个文件夹是一条检查项。
2. 选出要用的文件夹：名称以「通用」开头的都用；其余按名称开头的业务判断，项目里有这项业务才用。比如项目接了付款码支付，才用「付款码支付-…」；项目做了退款，才用「退款-…」。没选中的文件夹不检查，但仍要写进结论：`规则` 与 `测试用例` 都记 `不适用`，并在 `规则依据` 里写明理由（如项目未接入退款），不静默跳过。
3. 读选中文件夹里的 `规则.json`；有 `测试用例.json` 时也读。
4. 按下面「怎么用」检查项目，并按「结论」给出这一条的结果。

## 适用性

- 文件夹前缀只区分**产品与业务能力**：以「通用」开头的，不限产品、不限 API 版本、不限商户角色，所有微信支付接入都要查；以具体产品或业务能力名开头的，项目有这项产品或业务才查。
- 本目录下的规则**不区分 APIv2 与 APIv3**，也**不区分普通商户与服务商**，这两个维度一律视为通用。API 版本和商户角色都不得作为排除理由，也不得因规则措辞看起来像某个版本就判不适用。
- 将来某条规则在不同版本或角色下流程确有差异时，由该规则文件内部写明，不靠文件夹名表达。

## 怎么用

`规则` 和 `测试用例` 各做各的。两个都有时，两件都做，各写各的结论。

"规则" 文件的内容当作 code review 的规则。阅读被测项目的代码，对照规则 JSON 的 `正确流程`。若不符合正确流程则判定为不通过。结论来自读到的代码。

其中规则json字段的解释：
| 字段 | 含义 |
| --- | --- |
| `正确流程` | 项目应有的行为 |
| `反例` | 有这个字段时，若出现其中的行为即可直接判断为不通过 |

测试用例是让你按照文件内的内容去写测试并运行，用运行结果下结论。只读代码、没有运行测试，不能把测试用例记为通过。没有 `测试用例.json` 时，不编写、不运行测试。

其中测试用例 JSON的字段解释：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 文件格式版本，不参与判断 |
| `id` | 用例标识，不参与判断 |
| `title` | 这条用例要确认的事 |
| `前置条件` | 开跑前要准备好的状态|
| `步骤` | 要执行的动作，按顺序做 |
| `预期结果` | 要看到什么，通常是某个 mock 每一次调用时请求参数该是什么。据此怎么判，见「测试用例怎么判」 |
| `禁止事项` | 有这个字段才遵守。它限制测试能调用什么 |

### mock

用项目已有的测试框架和 mock 工具。不改项目代码

- 只换项目直接调用微信支付的方法：SDK 客户端的方法，或项目自己封装的发请求函数。项目自己的业务方法不要换，换了就看不到项目自己发没发请求。
- mock 每次被调用都要记下这次调用和请求参数。预期结果按这些记录判断。
- 测试只调用测试用例写明的项目方法，不直接调用 mock。

## 结论

每个选中的文件夹返回一个对象，所有对象放进一个数组。下面以付款按钮防抖为例：

```json
{
  "title": "文件夹名称",
  "规则": "通过",
  "规则依据": "读到的代码位置，以及它有没有做流程里的事",
  "测试用例": "通过",
  "测试依据": "测试怎么写的，以及运行结果：各个 mock 被调用了几次、请求参数是什么、哪几条没判"
}
```

`规则` 取值：`通过`、`不通过`、`不适用`。`通过` 是 code review 看到代码做了 `正确流程` 里的事。`不通过` 是该做的事代码里没有，或做法和 `正确流程` 相反。

`不适用` 只在规则要检查的情况在这个项目里不存在时使用。比如项目只有后端接口、没有付款按钮，付款按钮防抖的规则记 `不适用`。

`测试用例` 取值：`通过`、`不通过`、`未观察到`、`不适用`、`无`。`未观察到` 指测试看不到项目发出要观察的请求，它不是结论，见下方「未观察到与禁止事项」。`不适用` 与规则同义，指要检查的情况在这个项目里不存在。当没有 `测试用例.json` 文件，结论里的 `测试用例` 写 `无`，`测试依据` 留空。

### 测试用例怎么判

按 `预期结果` 逐条判：

- 写的是某个 mock 每一次调用的要求：这个 mock 被调用了，就逐次检查；一次都没被调用，这一条不判。没被调用可能是项目没有这一步，也可能是这一步放在测试看不到的地方，测试分不清。项目有没有这一步，由规则读代码判断。
- 判了的条都符合，记 `通过`；判了的条里有一条不符合，记 `不通过`；一条都没能判，记 `未观察到`。没判的条不算不符合，在 `测试依据` 里写明哪几条没判。

### 未观察到与禁止事项

预期结果要检查的 mock 一次都没被调用时，按「测试用例怎么判」记为 `未观察到`。这时不要由测试自己去调用那个接口让 mock 被调用，也不要因为测试没观察到就把规则写成通过。

`未观察到` 仅适用于**测试已完整跑完、mock 有调用记录、而要观察的那个 mock 零调用**的情形。测试未编写、未跑起来或环境不满足时，不得记 `未观察到`，须在 `测试依据` 里写明原因。

测试只能用三种方式触发项目：调用步骤里写明的项目方法，由 mock 给出微信支付的应答，调用项目的回调方法送进一条通知。查单、撤销、重试这些后续请求，只有在这次触发的处理里当场发出，测试才看得到。

项目若把后续请求放在定时任务、延时队列、前端或收银台的轮询里，或者要等另一次请求才发出，测试就看不到，这一轮记为 `未观察到`。不要为了看到它去调用定时任务、改配置打开默认不启动的调度，或者调用前端用来查询结果的接口。项目有没有这一步，交给规则读代码判断。定时任务按项目默认配置在测试里自己跑起来、并在等待时间内发出请求的，照常检查。

### 名词解析

**业务订单**：用户在商户系统里进行结算后，后台存进数据库的那张待支付订单。它是商户自己的单据，不是向微信支付下的单。

- 一次结算对应一笔业务订单，用业务订单号区分。
- 购物车、还没提交的结算页都不算业务订单。
- 同一笔业务订单不管点几次支付，都还是这一笔，不会多出新的业务订单。
- 在项目代码里，它通常就是发起支付方法传入的那张订单，比如 order_id 指向的订单记录。
- 向微信支付下单时用的是商户订单号（out_trade_no），那是支付单的编号。有的项目直接把业务订单号当商户订单号用，这时两个号码相同，但仍是两样东西。
