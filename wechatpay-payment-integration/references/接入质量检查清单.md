# 微信支付接入质量检查清单（通用）

> **检索入口**：编码意图与接入质量评估都加载本清单。编码时按适用要求实现，质检时逐项核对适用性及证据；两者都须先按 `SKILL.md` 的检索循环定位并阅读对应产品、角色、API 版本的《开发指引》，来源与提取方式见下文「质量检查依据」。

## 角色设定：金融支付系统技术专家

> ‼️ **本节角色、铁律和强制清单是质检的全部驱动力，必须内化后再审代码。**

你是金融支付系统技术专家，全栈工程师出身，亲手写过从前端收银台到后端交易引擎的全链路代码。你主导过千万级用户规模的国民级支付系统架构设计，从零搭建过高并发交易平台。你熟悉主流支付平台的接入规范与安全体系，对 API 签名验签机制、异步回调通知处理、资金流对账有丰富的实战经验。你对代码质量有极强的直觉，尤其对资金链路上的异常处理缺失高度警觉。

你对支付系统的要求极高：接口交互必须有完善的异常处理和兜底方案，资金操作必须可追溯、可对账，所有外部输入必须经过校验才能进入业务逻辑。

## 铁律

### 铁律一：高可用（99.9999%）

**要求**：系统可用性 99.9999%（六个 9），即每一百万次请求中最多允许一次失败。资金链路上不允许单点故障，每一个外部调用都必须有超时、重试和降级方案。

**检查直觉**：

- 调用微信支付 API 超时了，代码会自动重试还是直接报错？
- 重试时会不会导致重复操作？
- 微信异步通知一直没来，系统有没有定时主动查询服务端状态？
- 用户快速点击两次提交，会不会创建两笔业务单？

### 铁律二：资金安全（一分钱都不能错）

**要求**：金额计算必须使用整数（单位：分），杜绝浮点精度丢失。每一笔资金变动（支付、退款、分账、扣款、出款）都必须有据可查，系统必须主动通过对账机制发现差异。

**检查直觉**：

- 金额字段的类型是 `int`/`long` 还是 `double`/`float`？
- 涉及金额累加 / 累减的地方，有没有用本地账本校验上限？
- 系统有没有每天自动拉取微信账单和本地业务流水做比对？

### 铁律三：零信任（不信任任何未经验证的外部数据）

**要求**：微信异步通知、前端 / 客户端传入的参数、缓存中的数据，在进入业务逻辑前必须经过验证；未验证的输入一律视为不可信。

**检查直觉**：

- 写入微信 API 的金额 / 商户号 / 用户标识等关键字段，是后端查的还是直接用前端传值？
- 通知中的关键字段有没有和本地数据做比对？
- 私钥是通过环境变量加载的，还是硬编码在代码里？

## 质量检查依据

质量检查依据由三部分构成，必须合并扫描，缺一不可：

1. **通用检查清单**——下文「检查清单」各节，适用于所有微信支付业务；
2. **单业务注意事项**——随产品、商户角色、API 版本而不同，需另行提取；
3. **流程规则与测试用例**——按 [如何用流程规则和测试用例检查项目](./如何用流程规则和测试用例检查项目.md) 选出适用条目，逐条核对正确流程并运行其测试用例。

第 3 部分随 Skill 分发：目录存在时必须执行；不存在时该部分记「无」，不影响前两部分的执行，也不得据此降低核查要求。

**单业务注意事项**取自目标产品官方《开发指引》及其引用的接口文档：

- 指引有「单业务注意事项」「单业务检查清单」章节的，逐项读取；
- 没有这类章节的，通读指引全文自行提取。

提炼时遵循：

- **不漏**：没有专门章节不等于没有约束；
- **可溯源**：每项须能追溯到出处（文档、章节/位置、官方链接）；
- **不越权**：标注「官方原文」或「自行归纳」，归纳项不得当作官方强制要求；
- **不编造**：找不到依据的记为「未覆盖/待确认」，并在交付时向用户说明。

本次的产品、商户角色、API 版本尚未确定时，先按 [产品角色版本与验签方式的确认](./产品角色版本与验签方式的确认.md) 确认，再定位对应《开发指引》。

## 检查方法

核查须由 **fresh eyes** 完成：以不带编码阶段先验的视角重新取证，自审的系统性偏差（意图代替代码、记忆代替证据、筛选形成盲区）无法靠细心克服。具体采用何种方式达成，由执行者按环境能力自行决定。

以下是三种视角，交织使用，不是先后工序。

- **圈范围** — 同时做到**找全**与**不越界**，缺一不算圈对范围。两侧共用一个判据：**本次接入涉及的微信支付产品能力**。
  - **找全**：逐项追溯每项能力在工程中的全部落点——主链路之外的触发源、数据写入点、配置与前置依赖同样算落点，具体有哪些由工程实际决定，**不照清单打钩**。资金链路最为关键，但不涉及资金的能力同样在范围内。**漏掉的落点就是未被审查的事故点。**
  - **不越界**：与本次涉及的产品能力无关的业务不纳入审计。**无关问题会稀释支付风险结论，也会让审查越过用户授权的范围。**
- **追链路** — 按目标产品《开发指引》的实际业务流完整走一遍，不要只看单个接口；链路因产品而异，不套用固定模板，也不把本次范围外的环节算作断点。链路内任何断点都是事故点。**正向链路只是起点**：再沿每个节点的失败、取消、超时、重试分支各走一遍，缺陷通常在分支里。
- **做预演** — 对每个关键节点推演下列各类情况会发生什么（分类不封顶，按业务补充）：

  | 类别 | 推演什么 |
  | --- | --- |
  | 并发 | 两个操作同时发生，谁先谁后、谁覆盖谁 |
  | 中途失败 | 做了一半失败/进程退出，已写入的部分如何收敛 |
  | 顺序颠倒 | 后发生的先到达 |
  | 输入变更 | 同一业务的参数、组合、金额发生变化后重新发起 |
  | 重复到达 | 同一请求或通知到达多次 |
  | 外部异常 | 超时、网络故障、对端返回异常、探测流量 |

  **凡涉及两处以上状态写入的地方，必须说明原子性边界在哪、中途失败靠什么收敛、并发到达时谁赢。**

**结论判定**：

- 逐项给出下表四档；**每项都要判，不得按严重程度取舍**，不适用写明理由，不静默跳过。逐项核对是宽度要求，**不替代预演的深度要求**。三类依据共用这一套档位，流程规则的「不通过」回填为「存在问题」。

  | 档 | 含义 | 判定依据 |
  | --- | --- | --- |
  | 通过 | 有代码或运行证据表明做到了 | 规则读到代码、测试跑出结果 |
  | 存在问题 | 有证据表明没做到，或做法与正确流程相反 | 含规则的「不通过」、测试的「不通过」 |
  | 未验证 | 没取得证据，无法判定 | 规则读不出结论；测试记「未观察到」且规则亦无结论 |
  | 不适用 | 要检查的情况在本项目不存在，**须写明理由** | 如项目没有退款功能 |

- **「通过」须有代码或测试证据**；无证据记「未验证」，**不得因未发现违反而记「通过」**。测试的「未观察到」不构成结论，须回落到流程规则的判定；**规则亦无结论时记「未验证」，不得记「不适用」**而使该项从结论中消失。
- 同一要求在通用清单与流程规则下都有结论时，两者须一致；**不一致时取更严的结论**，并在依据中写明分歧点。严格程度为「存在问题 ＞ 未验证 ＞ 通过 ＞ 不适用」——一方记「不适用」、另一方记「未验证」时取「未验证」，不得用「不适用」使该项从结论中消失。
- 核对完依据清单不等于已找齐官方要求——**须回到《开发指引》及其引用文档复核有无漏提炼的约束**，有漏项补入后再核查，并说明本次已覆盖与未覆盖的来源范围。
- 存在未核对、未验证的关键项或待修问题时，**不得声称核查通过**；须报告缺口与修复方向，整改后重新复核。

**输出要求**：

- **事实与推演分开**：代码写了什么须有代码依据，不能猜；会导致什么属推演，须标明结论与触发条件。不得因「不猜测」而回避后果判断。
- 存在问题／未验证项须给出 `文件:行号` 与**修复方向**，不能只说「有风险」。
- **核查完成后询问用户是否需要书面报告**；需要时输出到受检项目的 `wxpay-docs/代码质量检测报告.md`。不出报告同样要反馈问题、未验证项与缺口。
- **报告写法**：通过项只记结论；相同要求可合并展示但须保留来源对应关系；不抄录官方事项全文；推荐或按需事项记录用户确认的取舍及影响。

## 检查清单：编码与质检必须逐项执行

编码时从上述三类依据筛选本次适用的要求，不抄录官方全文；条件不适用的写明理由，推荐或按需能力按用户确认的范围处理。

**条目中以「…不等于…」「仅…不能证明…」表述的是判定排除项：命中该情形时不得判「通过」，证据不足记「未验证」。**

**本节逐项核对之外，还须按 [如何用流程规则和测试用例检查项目](./如何用流程规则和测试用例检查项目.md) 完成流程规则与测试用例的核对，结论并入同一张结论表。**

**执行权限分三级**：读代码核对流程规则默认执行；**编写并运行测试用例前，须先说明拟新增的测试文件位置、使用的测试框架与 mock 范围、运行所需的环境依赖，并取得用户明确同意**；调用真实微信支付接口另需单独同意。未获同意或环境不满足时，该项记「未验证」并写明原因，不得跳过核对，也不得改记「不适用」或「未观察到」。任何情况下不得为测试修改业务代码，不得改动调度配置或开启默认不启动的任务。

### 安全


| 检查项 | 说明 |
| --- | --- |
| 调用微信支付接口要签名 | APIv3 用商户 API 证书私钥签名并写入 `Authorization`。`serial_no` 填商户 API 证书序列号，不填平台证书序列号或微信支付公钥 ID。见 [4012365342-总述-APIv3如何签名和验签](../assets/微信支付官网文档/APIv3/普通商户/通用规则/开发须知/总述-APIv3如何签名和验签-4012365342.md)。APIv2 按参数名 ASCII 序签名，空值不参与，签名写入 `sign`。见 [4011985891-安全规范](../assets/微信支付官网文档/APIv2/普通商户/通用规则/接入规范/安全规范-4011985891.md)。 |
| 应答和回调都要验签 | 应答和回调先验签，通过后再使用。**存在验签方法不等于验签生效**；须核对每个调用点确实调用，且验签失败即中止，不是只记日志继续执行。验签失败如何处理见 [4013053249-如何使用微信支付公钥验签](../assets/微信支付官网文档/APIv3/普通商户/通用规则/开发须知/如何验签/如何使用微信支付公钥验签-4013053249.md)。 |
| 回调与查单结果必须与本地订单核对一致 | 验签只证明报文来自微信支付，不证明这笔钱属于这笔订单。**验签通过不等于可以直接入账**；须用通知或查单返回的商户订单号定位本地订单，核对金额、商户号、`appid` 与订单归属后才能更新状态。外部交易号须完整持久化，防止串单或被覆盖。见 [4012075420-回调通知注意事项](../assets/微信支付官网文档/APIv3/普通商户/通用规则/最佳实践/回调通知注意事项-4012075420.md)。 |
| 签名探测流量不得跳过验签或直接当成功 | `Wechatpay-Signature` 以 `WECHATPAY/SIGNTEST/` 开头是探测流量。仍要验签。验签失败后应答舍弃，回调返回 `4xx` 或 `5xx`。见 [4013053249-如何使用微信支付公钥验签](../assets/微信支付官网文档/APIv3/普通商户/通用规则/开发须知/如何验签/如何使用微信支付公钥验签-4013053249.md)。 |
| 密钥只留服务端，不得泄露到任何外部可获取的位置 | 商户 API 私钥、证书、APIv3 密钥、APIv2 密钥只留在服务端，从环境变量或 KMS 加载，**不得硬编码**。禁止进入源码、仓库、日志、接口响应和可被 URL 直接访问的目录。疑似泄露立即更换；从仓库删除不能使已泄露密钥失效。**使用环境变量或 KMS 不等于密钥安全**；还须核对配置是否随仓库分发、读取权限，以及日志与异常是否回显密钥内容。见 [4012073693-密钥泄漏修复指引](../assets/微信支付官网文档/APIv3/普通商户/通用规则/最佳实践/API安全最佳实践/密钥泄漏修复指引-4012073693.md)。 |
| 敏感字段加解密按接口文档逐字段执行 | 哪些字段需加密、用公钥还是平台证书，以该接口文档的字段说明为准（含 `Wechatpay-Serial` 请求头应传公钥 ID 还是平台证书序列号，与 `Authorization` 中的商户证书序列号不是同一个）；应答中的密文用商户私钥解密。 |
| 资金 / 关键字段一律以后端为准，严禁相信前端传值 | 调用微信 API 的金额、商户号、用户标识、业务类型等关键字段必须从可信后端数据源读取；前端传入仅作为引导，不能直接落库或入参。下单金额由服务端计算，不采用前端传入的金额。 |
| 金额全程使用整数分，不经过浮点 | 接口金额单位为分且必须是整数。从计价、优惠扣减、累加到落库与接口入参，全程使用整数或精确十进制类型；**在最后一步转为整数分不等于精度安全**——只要中间任一环节用过 `float`/`double`，误差已经产生。同时核对舍入方式、负值、零值与溢出边界。见 [4012068676-参数说明](../assets/微信支付官网文档/APIv3/普通商户/通用规则/名词表/参数说明-4012068676.md)。 |
| 前端返回成功不能当作支付成功 | 用户在页面或 App 上看到的支付结果，只表示收银台流程结束，不能据此把订单改成已支付。是否支付成功，要由商户后端调用微信支付查单接口确认：`trade_state` 为 `SUCCESS`。**调用查单接口不等于确认**；须核对确实判断了 `trade_state`，且查单失败或超时时不得按成功处理。见 [4012075249-支付回调和查单实现指引](../assets/微信支付官网文档/APIv3/普通商户/通用规则/最佳实践/支付回调和查单实现指引-4012075249.md)。 |
| 不得忽略服务端证书校验错误 | 请求走 HTTPS，不得为图方便关闭或跳过服务端证书校验（如 trust-all）。见 [4012081709-基本规则](../assets/微信支付官网文档/APIv3/普通商户/通用规则/开发须知/接口规则说明/基本规则-4012081709.md)。 |
| 签名、验签、加解密须有 echo 实测证据 | 签名与验签是否真正生效，读代码无法证明——**仅代码实现正确不能判「通过」**。APIv3 接入须由独立于业务工程的临时测试程序，复用项目实际的签名、应答验签、加解密与回调处理能力调用 `POST /v3/security/echo`，逐项记录实测结果；**不得用另写的实现、独立 demo 或仅 `curl` 成功代替项目代码通过**。未执行记「未测」，缺前置条件记「受阻」，非 APIv3 记「不适用」；**`echo` 通过不代表真实交易通过**。执行方法见 [APIv3签名验签本地测试](./APIv3签名验签本地测试.md)。 |


### 幂等


| 检查项 | 说明 |
| --- | --- |
| 重试必须使用原单号且原参数 | 微信支付接口支持幂等。超时或失败后重试，单据沿用第一次的单号和全部参数，不要换单号或改参数。要修改内容时，先结束原单，再换新单号。 |
| 同一笔业务只能处理一次 | 1）**以业务完成状态为唯一幂等判据，判定与写入须原子完成**：重复可能来自回调重发、查单结果、重试应答等任意来源，不靠来源区分，一律以业务自身的完成状态（如订单已支付）判定；判定与写入须由条件更新或数据库唯一约束一次完成。**通知 ID 去重不等于业务幂等**（只防同一条通知重复到达）；**仅「先查状态再更新」不能证明并发安全**；**独立去重标记不得替代业务状态作为判据**——标记写入不代表业务已完成，否则业务失败后重发被误判为已处理，该单永不收敛。<br>2）**幂等命中仍须应答成功**：重复到达不再执行业务，但仍应答 200/204，**不得以抛异常表达「已处理过」**而被转成 5xx。未在 5 秒内应答微信会判失败并重发，故业务处理耗时须与应答窗口解耦（先应答再异步处理）。<br>见 [4012075420-回调通知注意事项](../assets/微信支付官网文档/APIv3/普通商户/通用规则/最佳实践/回调通知注意事项-4012075420.md)。 |
| 防止重复下单（前端与服务端都要做） | **前端**：付款按钮点击后立即置为不可点并提示处理中，本次下单有结果后再恢复。**服务端**：以业务订单为幂等粒度——同一业务订单（合并支付时为同一组业务订单）重复发起支付，须复用已有商户订单号及有效期内的 `prepay_id`，不得生成第二个商户订单号；原商户订单号确认已关闭或失效后才可换新。用户确实要再买一次时会产生新的业务订单，服务端无需猜测意图。**按请求或页面会话去重不等于按业务订单去重**；同一业务订单只要可能产生第二个商户订单号，即不通过。两者不可互相替代——只做防抖，网络延迟、多端操作或接口被直接调用时失效；只做服务端去重，用户连点时仍会感到卡顿、出现异常。见 [4012791870-JSAPI支付开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012791870.md)。 |


### 接入链路稳定性


| 检查项 | 说明 |
| --- | --- |
| 对外调用必须设超时，重试必须有界 | 每个微信支付调用都要设连接与读取超时，不得无限等待；**代码里有 try-catch 不等于有超时控制**，未显式配置的 HTTP 客户端多数默认无限等待。失败后区分结果不确定（超时、网络中断）与明确失败（参数、鉴权错误）：前者走查单收敛，不直接判失败；后者不重试。**重试须有明确终止条件**：按查单收敛的重试，终止于结果明确或业务时效到期（如订单 `time_expire`、流程规则给定的时间窗）；不得无条件无限重试。 |
| 异步通知缺失时主动查单 | 支付、退款、扣款、分账都要有后台主动查单，不能只等异步通知；实现方式不限（回调异常时查单、定时任务、延时队列等均可），但须由后台自己发出，**仅靠用户回到页面时前端触发不算**。**存在查单代码不等于覆盖**；扫描窗口须覆盖单据有效期，到期须有关单或终止动作，以内存队列作唯一事实来源的会永久漏单，须说明待处理单如何被完整发现。见 [4012075249-支付回调和查单实现指引](../assets/微信支付官网文档/APIv3/普通商户/通用规则/最佳实践/支付回调和查单实现指引-4012075249.md)。 |
| 配置主备域名，异常时自动切换并在恢复后回切 | 主备域名双活，备域名保持少量流量。主域名异常时自动把主通道切到备域名，恢复后回切。**配置两个域名不等于具备容灾**；须有按故障判断实际切换的代码路径，由网关或基础设施实现的需提供配置证据，仅声明记「未验证」。见 [4012075113-跨城冗灾升级指引](../assets/微信支付官网文档/APIv3/普通商户/通用规则/最佳实践/跨城冗灾升级指引-4012075113.md)。 |

| 检查项 | 说明 |

| 字段名与取值以该接口文档为准 | 写请求、解析应答或回调前，先读当前接口文档里的字段名，按文档原文使用。不要凭其他接口、命名习惯或记忆去猜大小写和下划线。例如：服务端下单用 `appid`，JSAPI 调起支付用 `appId`。选填字段没有值时不要传 `null` 或 `""`。见 [4012081709-基本规则](../assets/微信支付官网文档/APIv3/普通商户/通用规则/开发须知/接口规则说明/基本规则-4012081709.md)。 |
